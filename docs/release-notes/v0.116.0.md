# claycore v0.116.0

Covers minors 0.114.0 through 0.116.0. The previous tag is v0.113.0.

**Read this one if you CONSOLIDATE, if you DRAG through the live door, if you
place a volume with a feather, or if you evaluate gradients on CUDA or OpenCL.**
Three of the changes below fix silent wrong output; one removes an unbounded
cost that a long session reached on its own.

## Three defects that produced wrong output, not slow output

**A topological move discarded the volume's feather** (#593, issue reported by a
host). `field::move_topological`'s `FieldVolume` overload is the only volume verb
that REBUILDS its result: it re-samples through a callable, and the free function
it forwards to takes a *region* rather than a volume, so bounds, cell size and
band were the only things that could cross. The feather had nowhere to ride.
`relax` starts from a copy and `flatten` edits in place, which is why neither has
the defect and why nothing in the suite caught it.

The displacement was correct throughout — 0.3832 of a 0.4 pull — so every
distance comparison stayed green while the result had a hard-edged box of visible
lattice around it. Measured by the reporting host on a verified-clean sphere, in
a roughness metric that sees a shading defect rather than a displacement one:
**1.756x** the reference roughness at a one-cell feather, **2.064x** at the three
they ship, **5.274x** at twelve.

The zero-displacement path is documented as "a drag that touches nothing hands
back the source" but in fact re-samples, so it dropped the feather by the same
mechanism. Both paths are fixed and both are covered.

**The live Move door dropped `gesture_id`** (#604 — issue #603, reported by a
host with a measured before/after). `clay_layer_move_surface` copied the field
into `MoveSettings`; `clay_sdf_move_begin` copied radius, ease, front_only and
steady and not that one. So every drag through the live door was unnamed however
the host labelled it.

That loses work rather than costing time. Unnamed, `continues_gesture` falls back
to comparing centre and radius bit for bit, so two SEPARATE presses at one anchor
compare equal: `moved_chain` REPLACES the first drag's grab with the second's
instead of stacking, and the first pull is gone. Two 0.25 pulls at x=1, r=0.35,
measured by the reporting host:

| door | surface | chain |
|---|---|---|
| held (named) | 1.1460 -> 1.2310 | 0->1->2 |
| live (named), v0.113.0 | 1.1460 -> **1.1460** | 0->1->**1** |
| live (named), this release | 1.1460 -> 1.2310 | 0->1->2 |

Both doors now read `clay_move_params` through one function (#606), so a field
added to that struct reaches both or neither. That is the class fix; the line
above was the instance.

**CUDA and OpenCL refused a gradients-only `eval_points`** (#580, ABI 0.114.0).
Both backends tested `!q.points_xyz || !out.distances` and returned
`InvalidInput`, where CPU, Metal and Vulkan accept a request that asks for
gradients or colours without distances. A host asking those two backends for
normals alone got an error and no explanation. Found while auditing why
`release_check.py`'s parity row passes vacuously for a backend that is not
registered in the build (#583) — an absent backend was being counted as an
agreeing one.

## A cost that grew without bound, and no longer does

**Regional consolidation ratcheted itself to whole-layer** (#601 — issue #595).
`plan_region_merge` grows its closure by every absorbed root's full influence
bound, and a previous bake is a root like any other, so re-baking the same patch
re-absorbed the whole of the previous one. The closure could only widen.

Measured on eight subtools with disjoint bounds, patch on one of them, the
requested box held IDENTICAL at every bake
(`benchmarks/move_subtool_closure_probe.cpp`, Mac, Release, CPU):

| bake | requested width | closure width | roots | bake |
|---|---|---|---|---|
| 1 | 0.620 | 1.72 | 1 | 80 ms |
| 4 | 0.620 | 6.64 | 2 | 572 ms |
| 8 | 0.620 | 13.68 | 2 (whole layer) | 2127 ms |
| 12 | 0.620 | 16.88 | 1 (whole layer) | 4098 ms |

The host asks for the same small patch every time and the twelfth bake costs
fifty times the first. A volume is a *sampled* field, so unlike a parametric
Subtract it can be partially re-absorbed; the planner did not distinguish them.
It now retains the unaffected samples and rebuilds only the patch, its removed
grabs' support, and a transition halo.

After, on the same fixture: **3396.9 ms -> 33.6 ms** at gesture 48, sampled width
16.880 -> 1.120, scene roots 1 -> 8, installed volume 6,947,300 -> 811,016 bytes.
Through 192 gestures the sampled width stays at 1.120 and storage below 837,260
bytes. Measured on Linux, GCC 13, Release CPU, single-run host measurements.

## Faster

**Every non-Mask brush release improved** (#602 — issue #531), measured on the
Linux application across ten alternating pairs of all 13 brushes, same host code,
fixture medians rather than per-run guarantees:

| brush | before | after |
|---|---:|---:|
| Standard | 21.772 ms | **16.216 ms** |
| Polish | 40.392 ms | 34.778 ms |
| Planar | 36.207 ms | 34.931 ms |
| Move | 62.234 ms | 56.519 ms |
| Smooth | 84.623 ms | 78.051 ms |
| Relax | 83.408 ms | 76.057 ms |
| Mask | 7.341 ms | 7.504 ms |

Five changes, each preserving exact field and mesh output: grab chains batched in
authored order; brick-local marching edges deduplicated before global welding,
with a contiguous exact-key table (at 141,000 edges, lookup allocations fall from
141,014 to **15**); zero-strength relax stencils skipped; shared lattice samples
reused while recording; source-fill grid coordinates generated in bulk.

Component medians on the same box: full gradient/colour sphere **36.603 ->
27.508 ms**, a 48-Grab sphere **39.351 -> 30.877 ms**, Smooth preparation 80.217
-> 72.679 ms, Relax 86.774 -> 78.639 ms.

## What moves under you

### The entry points

**`clay_region_merge.whole_layer` means something narrower.** It was "the closure
reached every visible root". It is now "every visible root fully absorbed", and
it is **false for a retained-volume patch even on a one-root layer**, because that
root's unaffected samples survive outside the bake. A host branching on this to
decide whether a region merge degenerated to a whole-layer one will now take the
other branch on documents it used to take the first on. `RegionMerge.box` now
reports the sampled patch including its halo rather than a whole-root closure.

**`clay_sdf_move_begin` now honours `gesture_id`.** A host that set the field and
(knowingly or not) depended on two same-anchor presses folding into one will now
get two stacked grabs and a surface that moves twice. That is the fix, and it is
still a change in output for code written against the broken behaviour.

**CUDA and OpenCL now accept a gradients-only `eval_points`** where they
previously returned `CLAY_ERROR_INVALID_ARGUMENT`. Code branching on that error
will stop taking the error branch.

**A decimating export should be read back.** `clay_mesh_params.decimate` is
unchanged in layout and meaning, but `clay_mesh_decimate_report` (ABI 0.115.0,
#584) now tells a caller whether the result is manifold, whether the input
already was, and how many simplifications ran. `clay_mesh_weld` forgets a stale
report rather than letting it describe triangles it no longer matches (#587).

### The formats

**No document or file format change in this release.** `clay_stroke_preset` grew
four fields — `rotate_to_azimuth`, `velocity_size`, `velocity_strength`,
`velocity_reference` (ABI 0.116.0, #586) — and `clay_decimate_report` is new;
both are APPENDS under the `struct_size` pattern, so a caller compiled against
the older struct passes the older size and never sees them. No field moved and
nothing was removed: `comm` over the exported symbols of v0.113.0 and this tag
reports one addition (`clay_mesh_decimate_report`) and zero removals.

## Every backend was verified on real silicon, for the first time

v0.113.0 was tagged with a 16/16 PASS table and **none** of the four manual
hardware gates behind it: the parity row asserts "every backend registered in
this build matches CPU scalar", and the release build registered `cpu` and
`metal`, so CUDA and OpenCL passed by being absent (#578). The gate record added
for that (#583) is why this release can say what it ran.

All four are RUN against this tree, on an RTX 5060 host, each control verified
BEFORE the runs to hide only what it claims:

| gate | evidence |
|---|---|
| cuda-parity | 565 assertions cpu-only, 1125 with CUDA (+560), 0 failed |
| nvcc-build | nvcc 12.0.140, compile line `--generate-code=arch=compute_90` |
| opencl-device | 1685 with CUDA and OpenCL, +560 over CUDA-only, 0 failed |
| **vulkan-device** | **no longer waived** — two real devices, 1125 each (+560), 0 failed |

Every backend contributes the same **+560**, which is the comparable quantity;
the totals are not, because the corpus grew since the +539 recorded at
e8ca6d59.

**`vulkan-device` had been waived since the record was created**, for want of a
host running the Vulkan backend on real silicon — lavapipe executes the
arithmetic on the CPU and is plumbing rather than a substitute. The fleet
acquired one, so the waiver was re-checked rather than carried forward, and its
premise had stopped being true. Both runs pinned `VK_DRIVER_FILES` to a single
ICD — NVIDIA RTX 5060 (Vulkan 1.4.312) and Intel UHD 770 (Mesa 25.2.8) — with
lavapipe present on the host and excluded, so neither run's arithmetic was on
the CPU.

Still unexercised, stated rather than implied: the CUDA runs reach Blackwell
through **PTX JIT only**. A cubin for sm_120 needs CUDA >= 12.8, so that half of
the architecture auto-detection has still never run.

## Known limits, stated rather than discovered

**#531 is NOT closed, and the 16 ms target is unmet.** Standard now sits at
16.216 ms against a 16 ms budget; Smooth and Relax remain near 78 ms. Results for
some actions are mixed — Polish release is slower on performance cores on one
fixture. The authors of #602 say so in the PR itself, and this release repeats it
rather than letting the improvements above imply otherwise.

**Decimation can still emit a non-manifold mesh at some ratios on some
toolchains** (#575, closed as attributed rather than fixed). Per-file impact is
one or two edges in 126k–210k triangles, watertight throughout. The root cause is
upstream of decimation: the mesher's own output depends on floating-point
contraction, and `-ffp-contract=on` and `off` differ by **24 triangles** on a
unit sphere at voxel 0.02, with 31 of 76 ratios pinching on one and 0 of 76 on
the other (#581). `clay_mesh_decimate_report` is how a host learns its export is
affected.

**A mesh is not byte-identical across toolchains.** Stated in `README.md` and
restated here: anything pinning a triangle count, a vertex position or a mesh
digest across compilers rests on something that moves.

**Regional consolidation's local path is narrow by construction.** It requires an
isolated visible hard-Add volume, identity node and layer placement, unit scale
axes, no rounding, gates or active replication, grab-only deformers with positive
radii and exactly zero easing outside their support, and no other visible operand
reaching the patch halo. Everything else takes the conservative whole-root path,
which is unchanged. Unchanged from the analysis in #540: a local closure needs
strictly non-overlapping bounds, and the cliff is at a gap of exactly zero —
0.005 of clear air, a quarter of a cell, moves a bake from 8 roots and 340 ms to
2 roots and 94 ms.

**`clay_stroke_preset`'s two new controls read channels only
`clay_stroke_sample_full` carries.** On the `count*5` float packing the other six
stroke entry points take, a barrel stamp faces a constant +x and the speed
response is off. `clay_stroke_resolve_full` into `clay_layer_place_stamps` is the
path that carries them. Unchanged from v0.113.0.

**Move still builds no stroke preset**, so spacing, pressure and lazy-mouse have
nowhere to land on it beyond `steady` (#532). Unchanged from v0.113.0.

**Native GPU execution of the #602 changes was not tested.** The measurements
above are CPU. The Metal parity leg passes, which says the backends agree, not
that the device is faster.

## Upgrading

Ordered by how much risk each item carries.

1. **If you branch on `clay_region_merge.whole_layer`, re-read that branch.**
   Its meaning narrowed and it now reports `false` in cases where it used to
   report `true`. This is the one change most likely to alter a host's control
   flow silently.
2. **If you drag through `clay_sdf_move_begin` and set `gesture_id`, re-test a
   double press at one anchor.** The second press now stacks rather than
   replacing. If your host was compensating for the old behaviour, remove the
   compensation.
3. **If you place volumes with a feather and then run a verb on them, expect the
   feather to survive.** It always should have.
4. **If you call `eval_points` on CUDA or OpenCL, you may drop the
   gradients-only workaround.**
5. **If you export with `decimate`, read `clay_mesh_decimate_report`.** It is the
   only way to learn that a particular ratio on a particular toolchain produced a
   non-manifold result.
6. **If you consolidate regions repeatedly in a session, you may stop working
   around the growth.** Re-measure your own maintenance policy against the new
   costs rather than carrying a threshold derived from the old ones.
7. **`clay_stroke_preset` gained four fields.** Recompile; pass
   `sizeof(clay_stroke_preset)` as `struct_size` to see them, or keep the old
   size and keep the old behaviour.
